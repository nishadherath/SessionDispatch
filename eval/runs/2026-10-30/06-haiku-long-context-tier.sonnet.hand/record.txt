### Step A: continue or hand off

The target class equals the current class and the table gives haiku a long-context tier (threshold 100,000 tokens). B + R = 96,450 is just under the threshold, so the short-path break-even does not apply and the stage is priced turn by turn (step 1.4.5), turn t reading C_start + (t - 1/2) * G.

```
G       = F + O                 = 3,000 + 1,500 = 4,500
C_end   = C0 + T * G            = 90,000 + 20*4,500 = 180,000
crosses = C_end > K             = 180,000 > 970,000 = false
C_cont  = C0 + T * G / 2        = 90,000 + 45,000 = 135,000   (average, for reference only)
C_fresh = B + R + T * G / 2     = 96,450 + 45,000 = 141,450   (average, for reference only)
```

Where the tier bites (turn t context, threshold 100,000):

- Continue: turn t context = 90,000 + 4,500*(t - 0.5). Turn 1 = 92,250, turn 2 = 96,750 (base prices); turn 3 = 101,250 and later (tier). So 2 base turns, 18 tier turns.
- Fresh: turn t context = 96,450 + 4,500*(t - 0.5). Turn 1 = 98,700 (base); turn 2 = 103,200 and later (tier). So 1 base turn, 19 tier turns. The first read of 96,450 is under the threshold, so cache_write at base.

Prices used (per million): claude-haiku-5-5 base: input 0.10, output 0.50, cache_read 0.01, cache_write 0.125. Tier (whole request over 100,000 tokens): input 0.50, output 2.50, cache_read 0.05, cache_write 0.625. Target and current are the same model. The handoff H is written at context 90,000, under the threshold, so at the base output rate.

### Adversarial pass

The opposite verdict, argued: hand off. A fresh session would hold only the handoff and the edit list, so its context is clean, there is no 90,000 tokens of history to carry, and the work is 20 mechanical turns, so there is no reasoning to lose. The handoff is cheap at 2,500 tokens. A fresh session would also be insulated from any stale facts in this session. But the baseline B is already 86,450 of the 90,000 here, so a fresh session saves almost nothing in context (3,550 tokens) and has to re-read 96,450 tokens, which is more than this session holds.

Each input, the way it could be wrong:

- C0: measured (90,000). If 30 percent higher (117,000), every turn is on the tier and continue costs more, but fresh still starts at 96,450, so fresh can win; recomputed below.
- T: plan estimate with no per-turn measure. If it doubles to 40, the fresh side's extra tier turn and its larger context keep it behind (per turn the gap is about 6,450 tokens x 0.05 USD per million, plus the one-off 0.0133 USD handoff and first read), so continue stays ahead and the margin grows.
- F and O (and the effort O assumes): both are defaults, not measured. Defaults were measured at high effort; effort here is medium so O is probably not under-stated. Tested F = 1,000 below.
- B and R: B measured, R measured at 10,000. If R were 20,000, fresh is worse still (more read, higher context).
- M (review pauses): none expected. A miss costs more on the larger fresh context, so any miss favours continue.
- Task type: a rename of a configuration key across docs with a reviewed list is mechanical. The only hidden design risk would be a key that appears in code, but the list is reviewed and the check script is the oracle. Held as matrix row 1.
- Prices: table 1 day old. The long-context tier is applied turn by turn, not on an average. If the tier were ignored (all base prices), continue would cost 0.0533 USD and fresh 0.0678 USD (27 percent apart), so continue wins either way.
- Unrecorded context: none, because the situation says everything is on disk. If something were unrecorded, writing it down would raise H and L would rise for fresh only.
